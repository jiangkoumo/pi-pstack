# Pause safely

Adapted from pstack by Lauren Tan. This workflow makes an explicit pause durable with local evidence; it does not commit, push, open or update a PR, merge, deploy, delete data, or clean up without separate authorization.

Before acting, read [Poteto mode for Pi](../SKILL.md) for the mode's tool and authority rules. Resolve that link from this playbooks/ directory: ../SKILL.md is the parent poteto-mode skill. An explicit pause request applies only to the current run and grants no new Git, network, delegation, or cleanup permission.

1. Pause only on an explicit request. "Keep going", "going to bed, keep going", or "do not stop" is not a pause. If the operator asked to continue, continue.
2. Stop at a safe boundary. Finish or back out of the current atomic step, start nothing new, and stop only the nested subagents recorded for this run. Use `subagent({ action: "status" })` to identify them and `subagent({ action: "stop", id })` to stop them, then wait for a terminal state. Do not stop unrelated background runs.
3. Take no irreversible action to pause. A pause request is not a commit request. Do not commit, push, open or update a PR, merge, deploy, delete data, or clean up a worktree unless the operator has separately authorized that exact action. If a PR or push already existed before the pause, leave it as it is and report it; do not extend it.
4. Make the work durable as local evidence before anything is removed or rewritten. Capture the current branch, worktree, HEAD, `git status --porcelain`, the tracked diff (`git diff --binary`), and the paths of untracked files. Write them under `<run-id>/` in the pstack run directory provided in the system prompt (or an operator-approved path) as `state.txt`, `changes.patch`, and `untracked.txt`. Do not use `/tmp` as the only copy. If the project already has a decision trail or `/loop` ledger, append one `pause` row with pointers to these files instead of duplicating it. Keep evidence out of the repository unless the operator authorizes a path, and do not paste secrets or full command output into it.
5. Write the resume note off-context. Put `resume.md` in the same run directory. Record the intent and playbook, the exact stop point, what is verified versus merely attempted, the current branch/worktree/HEAD and whether the tree is clean, dirty, or broken, the child run ids, the authorization scope, next steps, key files, and gotchas. If a commit was already authorized and made, record its id; otherwise state explicitly that no commit was made. If the tree is broken, say so in one line and name the failing check.
6. Report the position in the loop, what is on disk versus only in the conversation (paths, not diff dumps), whether the tree is clean or dirty, any commits actually made, the resume-note and patch paths, and the first action on resume. This is a pause, not a final report. Do not describe local evidence as a commit, a push, a PR, or a clean tree.

The main skill owns authorization, delegation, and Git rules. This workflow preserves the current grant; it does not create a new one.
