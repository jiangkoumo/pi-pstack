# 背景与范围

## 项目缘起

用户发布了 [介绍 pstack 的 X 帖子](https://x.com/jiangkoumo_/status/2110955861896253763)，随后提出将 Cursor 中的插件移植到 Pi。讨论确认的产品形态是一个整体安装的 Pi package；本次工作将背景、来源和移植计划归档为独立项目。

帖子正文已在本次会话中通过 ego-browser 读取。它介绍了 pstack 的 poteto-mode 入口、工程原则、要求交出真实运行证据的验证方式，以及 correct 如何处理重复错误。正文是项目缘起的证据；实现细节以固定提交下的上游源码为准。

## 上游是什么

pstack 的作者是 Lauren Tan（@poteto）。官方仓库位于 cursor/plugins，主要内容是 SKILL.md、任务流程和代理说明。它将作者的工程判断和执行方法组织成可按需读取的材料。

值得保留的行为包括：

- 调查调用路径、证据和数据结构之后再实现。
- 原则必须改变具体决策；说明原则名及其实际影响。
- 验证需要执行相关检查，并提供真实行为的证据。
- correct 从至少两次出现的同类错误中寻找可执行约束，优先架构，再类型、lint/CI，并验证行为；文档用于需要判断的部分。
- 主代理负责整合与核实子代理的工作。

这些是上游方法的概括，不表示移植版已经具备相同行为。

## 为什么适合 Pi

Pi 原生支持 Agent Skills 的 SKILL.md 形式，详细技能可以按需读取；Pi 扩展提供命令、生命周期事件和会话状态；Pi package 可以将技能与扩展一起分发。因此，内容层与运行时适配层可以分别维护。

Pi 核心不内置 pstack 所用的 Cursor Task 子代理协议。当前操作者已经使用 pi-subagents，多代理移植应对接该插件的实际接口。

## 已确定的方向

| 决定 | 理由 |
| --- | --- |
| 一个独立 Pi package | 一次安装，集中管理版本与资源 |
| 技能保持为文件，扩展保持精简 | 便于按需加载、审阅差异和更新上游 |
| 先验证日常工程闭环 | 原则、调查、修复、实现、correct 是当前最明确的价值 |
| 单代理能力可独立工作 | 多代理依赖缺失时仍应有明确可用范围 |
| 记录固定上游提交 | 避免追踪 main 时内容漂移而无法复现 |

## 当前范围与后续范围

操作者已授权开始移植。首批已实现 poteto-mode 的调查、修复和实现流程，以及八个原则、correct、tdd；当前验收边界见 [首批记录](port-status.md)。

完整的多模型竞赛、自动合并、通宵运行、大规模编排、跨聊天历史检索、界面控制工具链属于后续工作，需分别核对依赖并验收。初版不宣称与 Cursor 插件全功能等价。

## 操作者环境

初次建档参考 Pi 1.2.0；本批开发实际参考 Pi 1.3.0，已有 pi-subagents 和 ego-browser。独立审阅优先使用操作者可用的 opencode-go/deepseek-v4.1-flash 或 opencode-go/glm-5.2；实现时必须再次核实模型可用性，不主动选择 Claude Opus。

以上是当前操作者配置，并非分发给其他用户时的强制默认值。发布版应检测能力并允许配置。使用 pstack 不意味着授权推送、合并或破坏性操作；仍遵守用户当前任务范围和授权。
